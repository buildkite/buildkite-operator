Buildkite runners are installed in buildkite. KEDA scales each queue from Buildkite queue metrics:

  docker: queue docker, dind, persistent agents, 1-4 runners (Deployment buildkite-docker)

  kubectl get deployment,scaledobject -l app.kubernetes.io/instance=buildkite -n buildkite
  kubectl get pods -l app.kubernetes.io/component=runner -L buildkite.com/runner-pool -n buildkite

dind runner Pods include a privileged Docker daemon, so the namespace must allow privileged Pods (Pod Security Admission level "privileged"). If runner Pods don't appear, check the ReplicaSet events for "violates PodSecurity".

WARNING: dind needs nothing installed, but its privileged Docker daemon has host-level access to its node. It is not isolation: only run trusted jobs on dind queues.

Docker daemons for docker pull through the OCI accelerator, caching registry-1.docker.io, ghcr.io, public.ecr.aws:

  kubectl logs statefulset/buildkite-buildkite-operator-oci-accelerator -c oci-accelerator -n buildkite

3 peering proxies use stable DNS seeds through the headless Service buildkite-buildkite-operator-oci-accelerator-peers. Each Pod has its own ephemeral cache and peer identity; replacing all Pods loses all cached content. Rolling updates replace one Pod at a time without surging, so use at least two replicas for availability during updates.

The proxy uses the CA in Secret oci-accelerator-ca, and runners trust its certificate, copied to ConfigMap buildkite-buildkite-operator-oci-accelerator-ca-cert on every install and upgrade. Pods read both only at startup. After replacing the Secret, run helm upgrade, then restart the proxy StatefulSet and those queues' Deployments.
